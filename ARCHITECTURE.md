# MiLingo Project Structure

This document explains the architectural decisions and folder organization.

## Architecture Pattern: Feature-First + Clean Architecture

### Why Feature-First?

- **Scalability**: Each feature is self-contained and can grow independently
- **Team Collaboration**: Multiple developers can work on different features without conflicts
- **Code Discoverability**: Related code lives together, making it easier to find
- **Testability**: Features can be tested in isolation

### Clean Architecture Layers (within each feature)

1. **Presentation Layer** (`screens/`, `controllers/`)
   - UI components and state management
   - Controllers use Riverpod for reactive state

2. **Domain Layer** (`models/`)
   - Business entities and logic
   - Platform-agnostic Dart classes

3. **Data Layer** (`repositories/`)
   - Data access and API communication
   - Abstracts data sources (Firestore, REST APIs, local storage)

## State Management with Riverpod

### Why Riverpod?

- **Type-safe**: Compile-time safety, no runtime errors
- **Testable**: Easy to mock providers in tests
- **Performant**: Only rebuilds affected widgets
- **Flexible**: Supports async, streams, and complex dependencies

### Provider Types Used

1. **@riverpod** (Code-generated providers)
   - Used for services, repositories, controllers
   - Auto-generated with build_runner

2. **Provider**: For read-only values
3. **StateProvider**: For simple mutable state
4. **FutureProvider**: For async data fetching
5. **StreamProvider**: For real-time data (Firestore streams)

## Routing with GoRouter

- **Declarative routing**: Define routes in one place
- **Type-safe navigation**: Use named routes
- **Deep linking**: Support for URL navigation
- **Auth guard**: Redirect based on auth state (to be implemented)

## Code Generation

Files with `.g.dart` suffix are generated by build_runner:

```bash
dart run build_runner build --delete-conflicting-outputs
```

Or watch for changes:

```bash
dart run build_runner watch --delete-conflicting-outputs
```

## Naming Conventions

- **Files**: `snake_case.dart`
- **Classes**: `PascalCase`
- **Variables/Functions**: `camelCase`
- **Constants**: `camelCase` or `SCREAMING_SNAKE_CASE` for compile-time constants
- **Private members**: `_leadingUnderscore`

## Best Practices

1. **Keep features independent**: Avoid cross-feature dependencies
2. **Use dependency injection**: Pass dependencies through constructors or Riverpod
3. **Separate concerns**: UI, business logic, and data access should be in different files
4. **Write tests**: Aim for >80% code coverage
5. **Document complex logic**: Add comments for non-obvious code
6. **Follow Flutter best practices**: Use const constructors, avoid unnecessary rebuilds
